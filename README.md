# Orchflow: orchestration of IoT-centric distributed workflows

A rewrite of **Orchflow**, the system from *Demo: Orchflow: Orchestration and Management of
IoT-Centric Distributed Workflows* (ICDCS 2024). The algorithms come from Amjad et al.,
*Orchestration and Management of Adaptive IoT-centric Distributed Applications*, IEEE IoT
Journal 2023.

Orchflow binds workflow tasks to edge devices that keep arriving and leaving. When a bound
device leaves, Orchflow re-selects a device and redeploys the task. The paper compares two
ways of doing this:

- **GOM** (Global Orchestration & Management): a central coordinator decides everything.
- **LOM** (Local Orchestration & Management): peer nodes rebind within their own cell.

The goal of this repository is to reproduce the paper's Table I (missed deadlines,
redeployment time, messages per redeployment) reproducibly, and to give us a clean base for
new work.

| Folder | What it is |
|---|---|
| [`orchflow/`](orchflow/) | **The new system (Python).** The same GOM/LOM logic runs in a seeded simulation and live over MQTT, and every event is logged so Table I is regenerated by one command. |
| `workflow-coordinator/`, `peer-node/`, `end-device/`, `workflow-authoring-interface/`, `execuateable-jars/`, `db_script/`, `deployment-source-files/` | **The original Java/PHP system.** Kept read-only as a reference for the port. See [Legacy system](#legacy-system). |

## Quickstart

You need **Python 3.11+** (3.12 recommended) and **[uv](https://docs.astral.sh/uv/)**. To
install uv, run `pip install uv` or see its docs.

```
git clone https://github.com/EshalSajjad/IoT-Centric-Workflows-Orchestration.git
cd IoT-Centric-Workflows-Orchestration/orchflow
uv sync --all-extras          # creates .venv with everything
uv run pytest -q              # the test suite
uv run orchflow plugins       # lists the registered protocols, mobility models, ...
```

If you don't use uv:
```
python -m venv .venv
.venv/Scripts/activate        # Windows; on macOS/Linux: source .venv/bin/activate
pip install -e ".[sim,live,analysis,dev]"
```

## Reproduce Table I (simulation)

There is one experiment file per Table I column, in `orchflow/experiments/`:

| | GOM | LOM |
|---|---|---|
| Plume modelling | `plume_gom.yaml` | `plume_lom.yaml` |
| Traffic monitoring | `traffic_gom.yaml` | `traffic_lom.yaml` |

```
cd orchflow
uv run orchflow run experiments/plume_gom.yaml               # 100 seeds x 60 simulated minutes
uv run orchflow run experiments/plume_gom.yaml --seeds 5     # quicker
uv run orchflow table1 results/plume-gom-<timestamp>         # mean and 95% CI across seeds
```

- **Speed:** one seed takes a couple of seconds.
- **Output:** every run writes `results/<name>-<timestamp>/seed-NNN/events.jsonl`, and all
  metrics are computed from those logs.
- **What can differ from the paper, and why:** see
  [`orchflow/docs/deviations.md`](orchflow/docs/deviations.md). In short, message counts per
  redeployment are deterministic and match the paper for GOM (8) and LOM traffic (6). The
  paper's single-run numbers are compared against our mean ± 95% CI over many seeds.

## Run live

The same experiment files run as real processes talking over MQTT.

| Where | How |
|---|---|
| **One process, no broker** | `uv run orchflow run <exp>.yaml --broker memory` (set `runtime: live` in the YAML) |
| **One machine, Docker** | [`orchflow/deploy/local/`](orchflow/deploy/local/README.md): `docker compose up --build` |
| **Several VMs (Oracle or local)** | [`orchflow/deploy/vm/`](orchflow/deploy/vm/README.md): bootstrap the VMs, then `orchflow_vm.py run <exp>.yaml` from your laptop |

## Contributing

- **Branches:** work on your own branch and open a PR to `main`.
- **CI:** [`.github/workflows/orchflow-ci.yml`](.github/workflows/orchflow-ci.yml) runs ruff,
  pyright and pytest, including against a real Mosquitto broker.
- **Before a PR**, from `orchflow/`, run:
  ```
  uv run pytest -q
  uv run ruff check src tests deploy
  uv run pyright
  ```
- **Behaviour changes:** if you change behaviour relative to the paper or the legacy code, add
  a row to `docs/deviations.md`.
- **Work split:** the shared contract is `src/orchflow/core/`. Each track owns its own
  folders, listed in `AGENTS.md`.

## Legacy system

The original implementation is kept unchanged for reference. **Don't port it, and don't use
it for new results:**
- it has no instrumentation for Table I's metrics;
- its shipped jars don't match its source.

The details are in `orchflow/docs/protocol.md` §6 and `deviations.md`.

| Component | What it was | How to run it |
|---|---|---|
| `workflow-authoring-interface/` | PHP/JavaScript web UI for drawing workflows and registering services | [its README](workflow-authoring-interface/Readme.md) |
| `workflow-coordinator/` | Java coordinator: the GOM/LOM binding and adaptation | [its README](workflow-coordinator/Readme.md) |
| `peer-node/` | Java peer node: runs within a cell, watches its devices (Moquette/Paho MQTT) | via the coordinator README |
| `end-device/` | Java plus Python/OpenCV agent for the IoT devices | via the coordinator README |
| `execuateable-jars/`, `db_script/gom.sql` | Prebuilt jars, MySQL dump | [`SETUP.md`](SETUP.md) has the distributed setup notes (JDK 8, Tailscale, DB fixes) |
